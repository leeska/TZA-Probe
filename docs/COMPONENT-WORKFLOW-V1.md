## 当前实施增量

`componentworkflow` 已实现内部精确计划、批准及持久步骤收敛：
计划绑定目标登记、组件、可信适配器版本、前置状态、发行版、配置、策略、迁移、
主控效果及保留规则；所有绑定使用严格 JSON 和规范摘要，步骤只接受固定类型。
可信适配器必须进一步验证配方顺序及具体业务语义；通用摘要本身不是执行授权。

每次 `Runner.Advance` 最多推进一个步骤。执行中检查点先 fsync，再调用适配器；
成功证据持久化后才推进。失败及丢回复只进入未知状态，下次只读核对，
证明没有执行后才允许使用原步骤 ID 重试，并保留原非执行证据。
已开始的批准效果可在批准起始窗口之后收敛；未开始的流程及证明未执行的首步骤
不能在窗口过期后启动。每个后续效果仍重核主控授权、本机开关、可信内容和准入，
不能借恢复绕过撤销。窗口、任务有效期和具体适配器约束分别核对。

结果在主控确认前保持待确认记录；确认后归档，同一个工作流 ID 的重复投递读取归档，
不再次执行。损坏记录或不匹配的恢复证据阻止推进，不删除诊断材料。
计划限制为 32 KiB，最多 32 步、每步 16 次且总共 64 次尝试；
每项证据只保存最多 1 KiB 的有类型输出引用，避免执行后收据过大无法写入检查点。
测试用无浏览器文件组件覆盖落盘失败、丢回复、重启、过期、资源等待、撤销、
检查点篡改和重复确认；这不是实际 IPSentinel 全流程验收。

Agent 已将旧安装 journal 的生命周期锁作为共享锁：有未确认旧回执时禁止新组合接管；
有组合待确认记录时旧通道不能执行新的生命周期操作，即使新进程已经释放文件锁。
旧通道原回执仍能优先补传。旧安装没有组合目录时不创建新目录，不重写原文件。
主控侧另以持久所有权和版本化交换端点阻止旧新通道并发改写。

IPSentinel 的新本地只读 `control policy-preview` 加载同一受保护策略并报告真实策略指纹，
不打开控制数据库、不 adopt、不启动服务或浏览器。它分别返回全量公共 catalogue 摘要、
选中的公共 Profile、权限和上限以及包含私有 URL 的本地策略摘要；私有 URL 不输出。
未来适配器必须从精确已核验发行版调用并比对签名 catalogue，不能信任任意命令输出。
此增量没有变更原策略指纹算法，也没有生成迁移批准。
`Release.ValidateEnablePolicyPreview` 已负责将预览的 runtime 版本、catalogue、
精确 Profile、权限和内外预算与已验签启用输入比对，再把策略指纹纳入联合输入摘要。
它不证明命令来源、私有 URL、路径或出口白名单本身；后续本地可信适配器仍须生成并核对这些输入，
不能将通过公共范围校验的字符串摘要当作已批准的真实策略。

`Release.EnablePolicy` 现按可信适配器固定的私有导航配方生成精确 TOML 和原策略算法指纹；
公共 Profile 的实际 origin 仍来自对应签名目录，不能由私有配方扩大。
Go 与 Python 都保留同一固定指纹向量。`ConfirmEnablePolicy` 同时核对公共范围及该精确私有指纹，
不接受只有格式正确但来源、URL、目录或出口不同的策略摘要。

首次启用配方由 `PlanEnableWorkflow` 生成，最多十步：
准备制品、安装、写策略、选版、采用空状态、启动、应用配置、核验、更新关联和恢复派发。
工作流及步骤 ID 在重规划时稳定，摘要绑定空状态、登记、签名发行版、精确配置、
策略文件、peer、服务摘要、外层资源、主控管理摘要和完整日程。
日程绑定配置修订 1、时区、服务、用途和时段，检查任务超时及预算；
未批准派发时省略恢复派发步骤。非空状态不能伪装成首次启用，arm64 不借模板获得不受支持的安装能力。

`EnableWorkflowBackend` 将精确配方编译为私有快照，向可信宿主发送固定类型步骤；
调用方或宿主修改传入对象不能改变后续步骤。文件宿主测试在十个边界分别丢失回复、
重建执行器并核对原持久证据，每步只执行一次；采用后替换业务实例被拒绝。
该文件宿主是本机测试实现，不等同真实运行组件已完成全部步骤。

Agent 本机宿主现已实现签名制品重新获取/暂存、固定参考安装器安装、
独立 worker 的私有配置/策略写入、选版及采用空状态。
选版恢复持安装锁核对 committed 事务、原空选择、配置与备份字节及完整安装；
prepared 事务或不匹配状态保留未知，不重新选择。
采用只调用精确已核验发行版的固定本机命令，降为独立 worker 且无补充组，
持安装锁并核对原选择和精确策略。恢复从原数据库读取身份，不重新生成。
这些本机配方已通过版本化组合请求接入；尚未完成本轮真实 Linux 成功启用验收。

IPSentinel 的 `control inspect-adoption` 不调用初始化或迁移，不创建业务身份。
它先取得原有服务与节点锁，然后核对私有数据库；无 WAL 时使用受锁保护的只读不可变连接，
存在 WAL 时只在隔离临时目录建立有界副本并读取已提交 WAL，不在原目录创建辅助文件。
副本限制为数据库 256 MiB、WAL 64 MiB，超限或异常保持未知，源文件不截断、不清理、不改写。
测试比较核对前后的全部原文件字节，并验证持锁竞争、策略/Schema 不符和损坏 WAL。

本机可信宿主还已实现服务定义创建、启动、精确配置应用与运行核验三个步骤。
服务定义按批准的原始字节摘要核对，拒绝其他来源的 unit、drop-in 和未重载的定义，
并核对开机启用状态及实际内核内存、CPU、进程数上限。启动使用共享节点资源监督器；
前置核对完成后，在记录启动尝试之前准入并预留资源，资源等待不消耗步骤重试次数。
服务文件及父目录同步完成后，在启动前持久保存 `starting` 边界。只读恢复不创建资源预留。
中断发生在该边界之前可以核对后续行；边界之后仅有 inactive 不能证明从未启动，
必须保留未知状态和资源预留，不重放启动或假装已清理。

配置由独立非 root peer 以原步骤 ID、原实例及原 epoch 下发，首版预期修订号固定为 0。
丢回复后只读取已有配置核对修订 1 和精确配置摘要，不再次生成修订。
若尚未配置但 epoch 已变化，不替换原 fence 后重试。
`control runtime-preview` 不打开控制库或创建身份；它与 Linux 启动共用原有运行指纹算法，
将实际安装元数据、浏览器清单、Playwright 和私有策略绑定到 descriptor 摘要。
启动回执允许“等待首版配置”的 degraded 状态；最终核验必须 ready，且实例、权限、
Profile、预算和配置均与批准一致，不能将仅版本号相同视为成功。

已补充 Agent 内置 `--component-effect` 受限权限执行入口及内部调用后端，
并已接入正常安装活动的版本化轮询分支、首启准备/审批入口和一次确认 UI，
但不宣称支持完整组合生命周期。
主控关联及日程已有事务实现、效果端点及 Agent 路由；更新/回退迁移及真实 Linux
完整生命周期验收仍需完成。
特权助手通过 `componentprivilege` 的私有请求、严格类型化证据和固定 systemd 启动器运行。
每次交付绑定原流程、步骤、计划和确切持久检查点；应用效果 ID 不因输入载荷变化而换号。
效果开始前 fsync 持久标记，成功回执保留；丢回复只读恢复，不能二次执行。
确认从未开始时先封存该尝试，拒绝迟到助手；新的尝试须来自下一版原流程检查点。
只读检查使用新的交付 nonce，成功结果消费后清理，不能复用过期 ready 或无限累积成功检查文件。
运行助手重核原签名、配方、节点本机禁用设置及两个原流程锁；
执行期间每 200 ms 核对原锁，原 Agent 不再持锁时取消子命令与等待，保留未知结果。

节点共享资源账本仍由原 Agent 管理；助手不能另开一份资源池，
也不能将助手自身的临时内存上限当作节点容量。助手只执行私有已批准记录中的固定本机效果，
父 Agent 保留流程锁、原资源预留和未知结果，不能把任意请求体或包提供的入口当作特权命令。
助手只读核对原 Agent 持锁的资源账本和精确预留，不重新初始化或重算容量。
主控关联与恢复排期不能作为节点特权效果执行。

当前专项覆盖独立进程重复交付、丢回复、落盘失败、迟到请求封存、输入篡改与锁失效。
Debian 13 上的跨进程与候选 Agent 拒绝未注册配方专项已通过；
该结果不等于正常 Agent 完整接受并执行了组合计划，也不代表全部特权步骤已现场验收。

主控内部登记保存原批准及首启配方，关联步骤原子建立 binding、配置修订 1 和停用日程，
后续独立步骤启用原已批准日程。流程确认前保留生命周期所有权，不接受旧安装通道或手动关联覆盖。
最终确认重新核对所有前置证据与精确终态回执；记录 cursor 不因管理关联提前前进。
恢复排期只调整原日程和派发门，不生成新的立即任务。主控核对尚未生效的尝试时原子封存，
防止已经报告 not_applied 后迟到的原请求重新产生效果。
Agent 先持久保存原运行核验完整证据，再发布其摘要；主控恢复时允许额外新鲜只读 Hello，
但原实例、epoch、配置、私有策略及 descriptor 必须保持，原证据摘要不能被替换。
当前持久化统一在 SQLite schema 29 新部署基线中初始化，不再逐代升级旧数据库；
参见 [新部署基线](FRESH-DEPLOYMENT.md)。

独立准备请求保存精确版本、原登记、业务出口/地区、签名管理包摘要及默认停用日程。
Agent 只核对空状态、固定服务、peer 和资源配方并返回精确计划；此时不下载依赖、
不安装、不启动、不采用业务数据库、不创建主控关联。准备与确认窗口为 15 分钟。
确认由主控管理员提交原计划摘要，服务器写入批准身份，原子插入唯一执行流程；
确认与取消互斥，丢回复可按原 ID 重放，已批准流程不能按准备请求取消来遗忘效果。
失败只返回受限诊断，不将主机错误或私有路径作为用户可执行输入。

准备、审批、主控效果及执行继续逐次检查原身份、权限、签名管理包和持久所有权。
日程默认停用，首启不额外产生业务任务。

## 组合暂停实现与验收边界

`ipsentinel-pause/1` 已提供精确计划和公共 Runner 后端：绑定原实例、epoch、配置修订、
已验证签名版本、运行指纹、私有策略、服务定义/限制、peer、原主控状态及日程摘要。
取消原任务单独进入批准摘要，默认不取消；所有数据保留，旧 drain 批准不扩权。
步骤固定为暂停派发、原任务收敛、确认记录送达和停止服务。

主控内部事务已支持取得生命周期所有权、原子暂停派发和持久步骤回执；
不改写原日程、绑定、配置及任务 ID。没有效果的未知尝试可在事务内封存，
迟到原请求被拒绝；已提交但丢回复时读取原回执，不重建身份。
终态确认绑定完整完成记录及停止观察摘要，首次确认仍核对原业务关联，
之后精确重放不依赖已关闭的 runtime socket 或新鲜 executor 心跳。

Agent 已有暂停步骤协调器、非 root peer 任务/记录通道和私有、fsync 的停机前证据保存。
固定 Linux 宿主已实现核验受保护安装锁、签名暂存及已安装文件、选中版本、
私有策略/运行指纹、专用 peer、固定非 root 服务定义与实际内核限制；
停止只调用原 Agent 的共享资源监督器，恢复核验进程树后回收原资源预留。
这不是新增包执行权限：复用内置受限预览命令，不接受插件自带命令或主机路径。
只读恢复只查询原任务、控制状态和双方记录游标，不暂停、取消、上传或 ACK。
仅对原收敛步骤提供 `in_progress` 证据和显式 continuation：保留同一持久尝试，
重新检查当前授权/就绪后继续稳定请求和下一页补传；未知 stop 不借此重复执行。
停止恢复必须存在属于原计划的停机前证据，并由宿主验证整棵进程树已清理，
不能凭 systemd inactive 或主控 dispatch_paused 宣称完整暂停。

当前回归覆盖配方权限变化、原身份变化、丢步骤回复、原尝试多次分页续行、
当前授权/资源拒绝、停机证据损坏、进程未清理、SQLite 失败回滚及实际 journal/事务恢复。
现已接入独立的 `ipsentinel-pause-effects/1` 能力、准备/审批 HTTP、正常 Agent 轮询
及一次确认界面。准备仅核对原签名版本和实际运行状态，不暂停派发或服务。
界面默认等待原任务自然完成；取消任务单独勾选并进入原计划摘要。
每次主控效果事务内重新核验当前会话，节点上的固定宿主逐次重新读取本机
`plugins.disabled` 和受保护的 `agent.json`，不因先前批准忽略后续本机禁用。
停止仍由原 root Agent 的共享监督器执行；没有赋予包新的特权命令或路径。
首启独立 helper 与暂停固定宿主是不同执行路径，不把前者的验收替代后者。

原启用准备和轮询显式排除暂停计划，避免旧 Agent 接收无法执行的配方。
正常协商可登记 controller-effects、enable-preparation 和 pause-effects 的完整集合；
未 opt-in 的原单能力响应不变。完成后先核验原停止证据并取得主控确认，
再持久保存完整签名作用域的 `workflow-paused.json`，最后归档原 pending。
丢确认或保存失败继续保留原 ID；暂停标记避免后续普通同步重连已停止的 socket 或重新预留资源。

## 用户入口与能力协商

用户选择功能、需要的节点和业务配置，在同一处查看准确版本、权限、出站范围、
资源上限及数据迁移，确认一次。详情页持续显示当前阶段、已完成步骤和必要的处理入口。
通知和目标集沿用声明式安装；不选择节点、不创建 Agent 实例，也不下载运行依赖。

新协议身份为 `tza.component-workflow/1`。
主控通过独立的已认证 capabilities 响应公布已实现能力；安装身份响应不增加字段。新 Agent 只在主控显式支持时，
向独立的组合登记/交换端点发送能力与请求。不得向旧端点的严格登记对象添加未知字段，
不得依靠版本号推测功能，更不能把新版响应发给未登记该能力的旧 Agent。
组合能力必须绑定当前 Agent 登记和新鲜度；旧 Agent 恢复连接不能继承新版会话的能力。
缺少双向能力协商时保留原入口，并明确需要更新管理能力。

独立端点前缀为 `/api/v1/agent/component-workflows/v1/`，提供
`capabilities`、`register`、`poll`、`inspect`、`apply`、`acknowledge`，以及
`prepare-poll`、`prepare-report`。管理端准备与审批位于
`/api/v1/admin/nodes/{id}/component-workflows/v1/preparations`。
原单能力仍为 `ipsentinel-controller-effects/1`；首启准备另经 opt-in 协商
`ipsentinel-enable-preparation/1`，暂停另协商 `ipsentinel-pause-effects/1`。
暂停的 poll/inspect/apply/acknowledge 和 prepare-poll/prepare-report 位于独立的
`/api/v1/agent/component-workflows/v1/pause/`，管理端为
`/api/v1/admin/nodes/{id}/component-workflows/v1/pause/preparations`。
这不公布尚未实现的组合更新、回退或移除能力。
会话 45 秒有效，每次旧安装上报作废前次会话，新请求必须重新登记。
主控效果事务重新检查登记、固定目标、权限和会话；核验实际安装签名管理包，
直到效果事务完成才释放包锁。轮询不创建批准、不扩充步骤或开始新业务任务。
未确认本机流程按原 ID 找回原计划；主控已确认而本机尚未归档时仍可取回同一批准。
完成后保存独立的签名终态标记再归档，记录同步不伪造旧通道格式。

新协议不改变原 `Enrollment` 的可比较性、旧回执格式及原操作 API。
组合登记与回执位于独立的版本化目录；原待确认回执优先完成补传。
同一节点组件只能有一个生命周期所有者；主控和 Agent 都需将旧安装通道与新组合通道
纳入互斥。未核对的旧执行中操作不能被新流程接管。

## 不可变计划与一次批准

计划格式为 `tza.component-workflow-plan/1`，采用公共严格 JSON 和规范摘要。
以下内容全部进入计划摘要，缺一项均不允许执行：

| 字段 | 约束 |
| --- | --- |
| `workflow_id` | 稳定 UUID，贯穿规划、批准、执行和恢复 |
| `target` | 精确主控、节点和 Agent 登记作用域 |
| `component` / `adapter` | 稳定组件 ID 和 Agent 内置适配器版本 |
| `intent` | `enable`、`update`、`rollback`、`pause` 或 `remove` |
| `before` | 当前安装、选择、业务实例、配置、策略和数据格式的精确前置状态 |
| `release` | 目标版本、签名键、包摘要、描述符摘要及各平台运行制品摘要 |
| `configuration` | 精确业务配置、引用修订、摘要及排期；凭据仅使用受控引用 |
| `policy` | 批准权限、所选 Profile、全部出站 origin、预算和内外层资源限制 |
| `migration` | 原与新 catalogue / 策略指纹、数据格式兼容判断和保留规则 |
| `controller_effects` | 主控包、安装记录、绑定和排期将发生的精确变化 |
| `steps` | 有序的受支持类型化步骤、前置条件和确定的输入摘要 |
| `retention` | 默认保留的业务配置、历史、数据库、Profile 和待确认记录 |
| `expires_at` | 批准及执行起始窗口，不能由后台静默续期 |

批准格式为 `tza.component-workflow-approval/1`，绑定工作流 ID、完整计划摘要、
目标作用域、批准者与时间。各步骤只继承这次批准中明确列出的效果，
不生成宽泛的永久批准，也不把未来任意计划自动置为已批准。
主控包的批准不能隐式赋予节点 root 执行权限；各端均验证本端效果在完整计划之内。

规划只读取有界的签名元数据、已核验缓存和本机状态，不启动业务进程。
执行前重核签名、撤回状态、节点本机禁用设置、目标身份、前置状态及资源准入。
权限取签名请求、用户批准、节点策略、适配器能力和实际平台能力的交集。
影响权限、版本、节点、业务范围、迁移或保留规则的变化使原批准失效；
普通进度、回执确认和已列明检查点的核对不要求用户重复确认。

## IPSentinel 的配置与策略来源

配置必须从精确签名包内的 `RuntimeDescriptor` 推导，
使用其中 `catalog_sha256`、`profiles`、Profile 的 `origins` 及运行制品信息。
不从未批准的运行时 Hello 扩大范围，也不继续将固定的三条 Google origin
作为所有版本的通用模板。
规划展示的是用户所选 Profile 的实际需求，并与权限和本机策略取交集。
执行后 Hello 的描述符、catalogue 和实际配置必须与批准结果一致。

0.4.1 与 0.4.2 的 catalogue 不同。即使 TOML 相同，
策略指纹也可能变化；更新及回退都需精确列明原与新指纹及允许的迁移。
不能关闭指纹检查、将全部 origin 自动加给旧版，或在运行后补一个未批准的扩权计划。
新流程保留旧 `EnableConfig` 路径的语义；版本化的配置推导由新适配器单独负责。

首次启用可以批准“该空状态下由本机生成一个新业务实例”，但不能接受任意外部身份。
实例生成后立即持久保存并绑定工作流；恢复只能读取该身份，不再次生成。
更新及回退保持原实例、数据库、Profile、预算和原逻辑任务 ID；
新 epoch 及配置修订必须满足适配器预先定义的迁移关系。

## 步骤、检查点与恢复

受支持步骤由 Agent 内置配方生成。包和远端不提供命令、Shell、
任意宿主路径或可执行钩子。步骤 ID 在规划时固定，输入摘要绑定父计划。
每个步骤先持久化执行中检查点，再调用可信适配器；
成功回执和输出引用落盘后才进入下一步，向主控确认后归档。

| 意图 | 后台收敛顺序 |
| --- | --- |
| 启用 | 能力/准入检查 → 核验和按需准备制品 → 安装/选版 → 写入精确策略 → 采用空状态 → 应用配置 → 启动/健康检查 → 校验身份与配置 → 主控绑定/排期 |
| 更新/回退 | 暂停新派发 → 核对并收敛原任务 → 补传/确认记录 → 停止并核实进程树 → 准备兼容版本 → 应用已批准迁移 → 启动并核对 → 更新绑定/配置 → 恢复已批准排期 |
| 暂停 | 暂停新派发 → 按原 ID 收敛或取消任务 → 补传/确认 → 停止并核实进程树 → 释放外层预留；保留数据 |
| 移除 | 完成暂停 → 检查其他实例/插件依赖 → 移除已列明的服务及管理关联；默认保留业务数据和历史 |

主控绑定及配置派发是工作流的可恢复步骤，不以激活成功作为完整更新完成。
更新后的暂停状态、授权及排期必须收敛；不得让用户手工重做已经精确批准的关联。
恢复排期不会额外创建实验或其他未批准的业务任务。

未知执行结果通过只读核对检查点、安装状态、进程和业务身份恢复。
无法证明未执行时不重新执行；无法证明清理时不释放资源。
网络失败不替换工作流、步骤、业务任务或去重 ID。

生命周期收敛基础已补：只补传记录的通道不再顺带领取新动作，
原任务按稳定暂停请求核对，明确批准取消时才使用稳定取消请求；
旧 drain 保持自然排空语义，不扩大原批准。主控只返回已经尝试且未终态的当前 binding 任务。
正常 drain 在持久补传、原任务收敛及 ACK 完成后才请求公共服务监督器停止并回收。
非 root peer 仅增加有界记录读取/ACK、原 Job 查询及取消；没有 run.submit、resume、
任意命令或新路径权限。实际 Linux 的 SO_PEERCRED 已验证新增操作使用非 root 身份，
但这项独立 peer 验收不证明完整组合更新、暂停或移除已完成。
已受理任务按原 ID 查询，投递尝试与逻辑任务分离。
资源等待发生在执行开始确认之前，保留批准与操作 ID；
尚未开始的流程在批准启动窗口过期后停止准入，要求重新确认精确计划；
已开始的流程仅能恢复原计划中列明的效果，不能扩充权限或换用新目标。

回退只选择已核验且数据格式兼容的精确版本。
不支持的数据库降级不能靠改版本号、复制活动数据库或重置预算完成。
不兼容状态停在有诊断的安全检查点，提供实际所需的迁移操作。
既有 root-only 服务需要明确的服务/权限迁移计划；不能当作普通新安装覆盖。

## 状态、数据与验收

界面将用户意图与实际状态分开：等待确认、排队、准备中、配置中、运行中、
暂停中、已暂停、需处理、已移除。内部保留步骤、资源等待、未知结果和最后有效状态。
“已暂停/已移除”必须有任务及进程收敛证据；健康失败或记录陈旧不能显示为业务成功。
删除业务数据需要独立明确授权；普通移除不执行该删除。
仍被引用的声明式目标集或共享组件先显示依赖并阻止破坏性移除。

实现必须覆盖：

1. 原协议/旧 Agent/旧回执兼容，能力过期和旧新通道争用。
2. 一次批准后的完整启用，以及权限、节点、制品、配置或策略变化后的拒绝。
3. 每个执行边界的重启、失联、重复回执和未知结果，只按原身份恢复。
4. 签名 catalogue 推导、精确策略迁移及旧版 origin 兼容。
5. 更新和回退保持数据、实例、预算、未确认记录，并自动完成主控关联和排期恢复。
6. 真正暂停/移除的进程清理、资源回收及默认数据保留。
7. 通知/目标集跳过节点、原生组件不需要浏览器、其他组件与 Agent 心跳不受失败影响。
8. 真实 Linux/Chromium 的启用、运行、更新、回退、暂停与移除，
   以及 390px 界面中的排队、错误、未知结果和恢复操作。
