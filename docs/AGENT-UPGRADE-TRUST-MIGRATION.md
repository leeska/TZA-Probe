# Agent 升级签名信任迁移

状态：整改代码与运维方案；尚未核验或修改生产信任，也未生成正式替代密钥。

## 已知失密的信任根

历史提交中的 Agent 升级私钥与本机现存升级公钥相匹配。旧公钥原 ID 为 `tza-agent-2026`，
解码后的 32 字节 Ed25519 公钥 SHA-256 为：

```text
d7138a63f6f0f74a48e1857e78041795a269b7cb2fdb01a32bde835c5d878d8d
```

这是 Agent 二进制升级密钥。CC 的 runtime 包签名密钥属于另一套信任，
不能混用或一并撤销。删除工作树私钥或更改 key ID 无法撤销已公开的旧私钥。

整改版本在 Agent 公钥加载、签名验证和私钥解析处拒绝该公钥，按公钥字节识别，
更改 ID 无法绕过。包含旧钥的信任文件会明确报错并停止该升级通道。
普通探测不依赖升级签名成功，保持其原有运行方式。

这项代码保护只对运行整改版本的程序生效。尚未迁移的旧 Agent 仍有原来的信任，
不能把仓库增加拒绝规则视为全网撤销完成。

## 发布前必须形成的清单

每台 Probe、提供 Agent 下载的服务和受管节点记录：

| 项目 | 必填内容 |
| --- | --- |
| 身份 | 运维资产 ID、主控与节点对应关系 |
| 信任 | 当前公钥 ID、解码后公钥指纹、文件属主和权限 |
| 发行物 | Agent 版本、架构、二进制与签名摘要 |
| 待处理升级 | 是否存在待应用的二进制及签名，原件备份位置 |
| 迁移渠道 | 已独立核实的 SSH/控制台或其他可信交付方式 |
| 验证 | 新钥合法升级成功、旧钥拒绝、普通探测与插件状态正常 |

典型节点公钥为 `/etc/tza-probe/upgrade-key.pub`；还需检查自定义 Agent 配置、
Server 数据目录的 `agents/`、构建时嵌入的公钥、CI 和离线签名副本。
清单不保存 token 或私钥内容。

## 执行顺序

1. 在隔离环境生成替代签名密钥，私钥权限 0600、目录 0700，放在仓库外并另行备份。
2. 构建整改候选，用隔离测试密钥完成双架构签名、下载、应用、拒绝旧钥和恢复验证。
3. 为每个生产目标准备明确的备份、候选摘要及新公钥指纹，再安排迁移窗口。
4. 通过独立可信渠道交付新公钥及已核验的 Agent，保留节点配置、身份和持久回执。
   新公钥的可信性不得仅由旧失密钥签出的升级包来证明。
5. 核验并隔离旧钥签出的待应用升级，替换节点信任文件，确认其中不再包含旧公钥。
   如需重启，先处理活动插件任务，保留未确认结果。
6. 更新 Server 下载目录和正式构建输入，仅分发新钥签出的制品。
7. 逐节点记录新钥正向验证和旧钥拒绝结果；不在线的节点维持“未迁移”，不能计入完成。
8. 处置工作树、构建缓存、制品缓存和历史私钥副本，记录 Git 历史清理的协作影响。

回退只使用已核验的软件和新信任根。不得通过恢复旧失密公钥来恢复自动升级。
未迁移节点、新钥正式签发、历史重写、推送和生产部署均需单独记录实际执行结果。
