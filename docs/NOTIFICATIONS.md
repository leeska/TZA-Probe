# 事件通知与 Telegram 模板

在后台“告警与通知”配置 Telegram Bot Token 和 Chat ID 后，可点击测试通知检查连接。渠道也可以是 Webhook，或一个已安装的通知插件（飞书、钉钉、企业微信、Bark、ntfy、Gotify 等，见下文「通知插件」与 [PLUGINS.md](PLUGINS.md)）。事件支持节点离线、到期续费、流量额度、达量降速、CPU 和内存使用率六类提醒。

## 消息格式

Telegram 使用纯文本，不解析节点名称中的 HTML 或 Markdown。消息按状态、节点身份、事件数据和时间分段，示例：

```text
TZA Probe · 🔴 告警触发
类型：CPU 使用率
节点：JP-NoSla-Gen2
节点 ID：节点唯一标识

分组：JP
地区：日本

当前 CPU：95.2%
触发条件：CPU ≥ 90%，持续至少 5分钟
指标采样：2026-10-13 15:30:00 UTC
规则来源：全部节点
重复提醒间隔：30分钟
本次条件持续：5分钟

事件时间：2026-10-13 15:30:00 UTC
事件编号：#123
```

- 节点 ID 用于区分同名节点，事件编号用于核对后台记录和通知重试。
- 已填写的分组、地区随事件记录；未设置时不打印空行字段。
- 时间统一明确标注 **UTC**，事件时间是事件产生时间，指标采样是 Agent 最近上报时间。
- 数据在事件产生时写入数据库。延迟投递或重试使用同一份快照，不用投递时的新指标替换历史值。
- 时长取最大的两个相邻单位并向下截断（如“2天12小时”“5分钟30秒”），不会把尚未到期的时间进位成已到期；不足 1 秒显示“不足1秒”。
- 正文超过 Telegram 的 4096 字符上限时截断正文并注明“内容过长已截断”，保留头部节点信息和尾部事件时间、编号，完整内容以后台事件记录为准。
- “本次条件持续”从服务端首次检测到条件满足时计算，包含规则设定的等待时间；它不等于未知的实际故障起点。首次立即触发的事件省略零秒持续时间。

## 各类事件包含的信息

| 类型 | 事件数据 |
| --- | --- |
| 节点离线 | 最后上报时间、未上报时长、45 秒离线判定和额外等待时间；从未上报的节点显示添加时间、首次接入宽限和安装排查提示 |
| 到期续费 | 到期时刻、剩余或已过期时长、提醒提前天数；已设置价格时显示金额及已填写的币种和周期，免费节点明确标记 |
| 流量额度 | 本周期已用量、额度、已用百分比、触发百分比、统计口径与计费周期 |
| 按额度降速 | 已用量、额度、百分比、统计口径、周期和商家声明的限速 |
| 按平均带宽降速 | 当前窗口平均带宽、配置窗口小时数、实际有数据的小时数和触发阈值 |
| CPU 使用率 | 当前 CPU 百分比、阈值、持续要求和采样时间 |
| 内存使用率 | 当前内存百分比、已用与总容量、阈值、持续要求和采样时间 |

流量单位采用十进制 KB / MB / GB / TB，与节点额度配置一致。降速状态是面板根据商家规则和用量推算的结果；消息明确提示实际限速仍需确认，不把推算当成测速证据。

到期提醒按实际时刻区分剩余与过期：过期 6 小时会显示“已过期：6小时”，不会因为不足一天而显示“今天到期”。

## 解除和重复提醒

解除消息使用中性的“⚪ 告警解除”，并带具体原因和当时的数据。例如：

```text
TZA Probe · ⚪ 告警解除
类型：CPU 使用率
节点：JP-NoSla-Gen2
节点 ID：节点唯一标识

解除原因：告警条件已解除
当前 CPU：20.5%
当前阈值：90%
本次条件持续：10分钟

事件时间：2026-10-13 15:35:00 UTC
事件编号：#124
```

CPU / 内存指标不可用（包括节点离线、Agent 采集或上报异常）时，暂停评估，不生成解除事件或新的重复提醒。已经触发的告警保留，后台「当前告警」显示「待确认」，注明读数是上一次事件快照；尚未满足持续要求的告警重新计时，不把缺失数据的间隔算成持续高负载。暂停状态保存在数据库，Server 重启后仍保留。

有效指标恢复后：读数低于阈值才解除；仍高于阈值则继续原告警，达到重复提醒间隔时可用新读数再提醒。暂停打断了连续观测区间，未知的间隔不计入消息中的持续时长。如果提醒规则被删除、关闭或不再覆盖节点，会解除并说明规则原因，即使指标仍不可用也不会留下永远无法清除的告警。历史事件与投递重试始终保留原始快照，暂停提示只附加在当前告警查询。

如果线路的降速声明被清除，降速告警的解除消息说明“线路当前未声明降速条件”，不显示 0 Mbit/s 阈值。

持续异常的重复通知在分组、地区之后的正文首行注明“提醒状态：异常仍持续（重复提醒）”，更新事件发生时的读数与条件持续时长。网络失败导致的同一事件重试仍使用原事件编号和原快照，不作为新的重复提醒。

连接测试消息只包含测试状态、Telegram 通道、说明和事件时间；不显示空节点字段或无意义的事件编号 0。

## 投递与兼容性

- 同一时间启用一个通知渠道：Telegram 或 Webhook。
- 失败使用指数退避重试，最多 10 次；只补发 24 小时内的未投递事件。查看后台事件列表中的发送次数与错误原因。
- Webhook 保持 `{ "version": 1, "event": { ... } }` 的字段结构；`event.message` 与后台记录一样包含分行数据，接收端按 `event.id` 去重。
- `event.message` 是给人阅读的文本，措辞和行序会随版本调整，**不属于稳定接口**（本版本起已从单句改为分行快照）。程序化处理请使用 `event.kind`、`event.active`、`event.node_id`、`event.at` 等结构化字段，不要按正文关键词匹配。
- 旧事件保留原有正文，新事件采用补全后的快照格式；无需数据库迁移。

## 通知插件

「告警与通知 → 配置出口」的渠道列表里会出现已安装的通知插件（在「插件」页从市场安装或上传，见 [PLUGINS.md](PLUGINS.md)）。选中后表单按插件声明的设置画出来；密钥类设置保存后不回显，留空表示沿用已存的值。同一时间仍只用一个渠道。

- 插件拿到的正文 `event.text` 与上面的 Telegram 消息内容一致，只是测试消息不带「通道：」那一行，也不按 Telegram 的 4096 字限制截断（超过约 8000 字才截断读数部分）。标题 `event.title` 形如 `TZA Probe · 告警触发 · CPU 使用率 · 东京`，测试消息是 `TZA Probe · 连接测试`。全部变量见 PLUGINS.md 的「模板」表；测试消息没有事件编号，`event.id` 为空。
- 发送：请求只能发往插件声明的域名（声明为 `*` 的发往你填写的地址），5 秒超时，不跟随重定向，回应最多读 64 KB；成功与否按插件的 `success` 规则判断（很多服务出错也回 HTTP 200，靠回应里的 `code` / `errcode` 判断）。
- 失败按同样的退避规则重试，最多 10 次。记在事件上的失败原因只写插件名与原因（如「飞书机器人 拒收：code = 19021」「ntfy 连接失败」），不含请求地址、请求头或回应正文，所以 Webhook 地址里的 token 不会出现在后台。
- 插件被删除或升级后不再接受原来的设置时，投递失败的原因会写明是哪个插件、该怎么办，配置出口也会提示；通知不会被悄悄关掉。正被用作渠道的插件不能删除，要先换渠道。
