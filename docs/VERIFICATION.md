## 2026-09-20 Agent 一键安装

- 新增 `internal/agentdist`：Server 公开提供 `/install.sh`（静态 POSIX sh，不含任何密钥）与 `/dl/tza-agent-linux-{amd64,arm64}[.sha256]`（支持 Range 续传，写超时放宽到 10 分钟）。二进制优先取数据目录 `agents/`，其次取构建时嵌入的副本；两处都没有时两个路由返回 404，启动日志有提示。后台“接入”弹窗改为直接给出 `curl -fsSL <server>/install.sh | sh -s -- --endpoint <server> --token <密钥>`，agent.json 折叠到“手动安装”里。
- 端到端：本机起 `0.0.0.0:25975` 的 Server，在 Docker 容器里用 systemctl 桩验证。Alpine（wget 路径）暴露了 `/etc/systemd/system` 目录不存在时脚本失败，已补 `install -d`；Debian bookworm（curl 路径）从 `curl | sh` 到后台节点显示在线（`2.0.0-dev arm64 linux`）全程通过。同一容器内再验证：不带 `--token` 重跑为升级并保留 `.previous`；`--interfaces ' eth0 , eth1'` 正确去空格写成 JSON 数组；非 64 位十六进制密钥被拒绝。
- 单元测试：目录副本优先于嵌入副本、校验和、Range 请求、非法架构名与路径穿越返回 404、脚本与仓库副本逐字节一致且不含 64 位十六进制串。测试用 `noEmbed` 开关屏蔽本机可能存在的嵌入二进制，CI 上无嵌入副本时同样通过。
- CI 发布任务改为先交叉编译两种架构的 Agent 放入 `internal/agentdist/bin` 再构建 Server，发布包里的 Server 自带一键安装能力。
- 视觉：接入弹窗桌面 / 深色 / 手机各一张，命令框与“复制命令”按钮并排，手机上纵向堆叠；`--token` 不再被 `break-all` 从中间截断。DOM 集成检查新增断言：弹窗里的命令必须精确等于 `curl -fsSL <base>/install.sh | sh -s -- --endpoint <base> --token <密钥>`。
- 补充：命令不再带 `sudo`。脚本非 root 时若有 sudo，会用 `sudo env TZA_TOKEN=… sh -c "curl … | sh -s -- …"` 重新拉取执行（管道执行时正文已被读走，无法原地提权）；参数从解析结果重建，`--interfaces`/`--nexttrace`（含单引号路径）原样传递。Debian 容器验证 root 直接执行、普通用户自动 sudo、普通用户无 sudo 明确报错、普通用户 sudo 升级四条路径。第一版在这里有两个 bug——`$@` 已被 `shift` 消费、`sed` 替换串少一层转义——都是容器里真跑才发现的。

### 同日修复：Linux 上从 TTL 0 探测（由部署方报出）

部署方在 Linux 上复跑 `TestEmbeddedTracesLoopback` 失败：
`send error (ttl=0, attempt=0): setsockopt: invalid argument` / `Reason: timeout`。
根因是两个 bug，都已修复：

- `trace.Config` 没有设置 `BeginHop`，库默认 0，于是第一个探测包带着 TTL 0 发出。TTL 0 不是有效跳数，Linux 直接以 `setsockopt: invalid argument` 拒绝并让整次追踪失败；macOS 容忍了这个值，所以本地没暴露。现固定 `BeginHop: 1`（与 NextTrace CLI 的 `-f 1` 默认一致）。
- 把 `res.Hops` 的**切片下标当成了 TTL**。库内部按 `ttl-1` 存（`updateHop` 用 `k := ttl - 1`，打印器传的也是下标），因此第一个跳会被丢弃、其余跳号整体错位一格，`StopReason.Hop`（存的是 TTL）也按下标去查。现统一 `TTL = index + 1`，`destinationHop` 用 `ttl - 1` 取下标；上一版为绕过服务端“TTL 必须 ≥ 1”而加的“跳过 ttl<1”是在掩盖症状，已删除。
- 回归：`TestEmbeddedTracesLoopback` 在 macOS 由 12 秒失败边缘变为 **0.3 秒通过**；新增 `TestMapTraceResultTreatsTargetHopAsArrival` 钉住“目标跳即到达”与跳号语义，`TestMapTraceResultKeepsEvidenceAndMasksAddresses` 改为按真实布局（下标 0 = TTL 1）构造。
- **仍未在 Linux 上验证**：本次尝试用 `debian:bookworm-slim` + 挂载的 Go 工具链离线编译来复跑，但开发机的 Clash（网络扩展 HakoMacExtension、DNS `198.18.0.2`、Fake-IP）在会话中途重新启用，容器内下载依赖被中间人证书拦截，`docker pull` 也超时，因此没有取得 Linux 结论。Linux 复验由部署方在目标机上执行。

## 2026-09-22 电信回程的 GIA / GT 判定改到中国侧

- 问题：生产节点上一条 CN2 GIA 回程显示成 `163 → CN2GT`。
- 定位：追踪方向是探针 → 中国目标，`cn2Label` 却读**第一条 CN2 跳之前**的跳来判断 GT。CN2 之前只剩电信自己的国际入口，而 `AS4134` 被无条件命名成“163”，于是 GIA 线路在链路里凭空多出一个 163，并被判成 GT。RIPE 实测 `218.30.0.0/15`（电信国际段）与 `110.184.0.0/13`（四川电信接入段）都属 AS4134，`202.97.0.0/19` 才是 163 骨干核心；`59.43.245.1` 在 RIPE 里没有 ASN，与「CN2 跳常缺 ASN」的现状一致。

## 2026-09-22 真凶：html / body 上的 overflow-y: auto（桌面测不出来）

- 现象：桌面 Chromium 怎么量都零位移，手机上（iOS Chrome = WebKit）一直「还是跳」。
- 机理：`html { overflow-y: auto }` + `body { overflow-y: auto }` 会让 **iOS/WebKit 把 body 变成
  滚动容器**：`window.scrollY` 恒为 0，手动锚定写 `documentElement.scrollTop` 是空操作（等于没接），
  `scroll` 事件目标是 body、`window` 上收不到，于是「滚动期间不动 DOM」的守卫在 iOS 上也从未生效——
  所以每次重绘都直接表现成跳。Chrome 会把 body 的 overflow 传播给视口，桌面端完全看不出差别，
  这就是我前面所有桌面实测都「零位移」的原因。
- 改法：
  - 删掉 `html` / `body` 上的 `overflow-y: auto` 与 `overscroll-behavior-y: auto`，交给视口滚动
    （`document.scrollingElement` 因此是所有内核下唯一正确的滚动元素）；
  - 守卫改在 **捕获阶段** 监听 `document` 的 scroll（元素级滚动也能触发），window 上再听一遍；
  - 位置写入同时写 `documentElement` 与 `body`（`setScroll`），多内核下都是免费保险。
- 验证（本地面板）：`scrollingElement=documentElement`、`body 不可滚动`、页面可滚 603px；
  用「在 body 上派发 scroll 事件」模拟 iOS 的事件落点：干净窗口 5 秒 **DOM 变更 0 次**、
  「最近同步」定在 13:28:04 不动，停止 2.5 秒后恢复（13:28:14）；

## 删掉滚动守卫：数字不必再停下来（2026-09-22）

## 2026-09-25 标签忽上忽下：先量频率与数据源，再补 IPv6 前缀粒度

- 现象：同一台 `us-vmiss-tri` 的联通回程一会儿 `10099 → 9929`、一会儿 `4837`、一会儿未知。
- 频率不是瓶颈（已量化）：任务 `bac58aa1…` 的 `route_interval=3600`，回程每目标每小时 1 次；6 台绑定节点合计 144 次/小时 ≈ 2.4 次/分钟，每次约 16 跳 → 每节点约 6 次 ASN 查询/分钟，只有数据源免费额度（ip-api 实测 `X-Rl` 上限 45 次/分钟/IP）的 ~14%。面板上 60 秒一跳的是延迟探测，它不查 ASN。
- 真正的缺口：近 3 小时里**有地址的跳只有 51%（IPv4）/ 47%（IPv6）拿到 ASN**，逐小时在 32%–82% 之间波动；`HK-ISVORO-Lite` 与 `hk-isvoro-litev6only` 是 0%（632 与 356 个有地址的跳，一个 ASN 都没解析出来）。拿不到 ASN 的跳只能靠前缀表命名，于是 `2408:8120:*`（9929 自己的地址空间）被 `2408:` 兜底读成 4837，移动的 `221.183.*` 读成未知——同一个路径不同时刻就显示成两样。
- 数据源核对：本机直接压测 ip-api——20 路并发全部 200、单次 10–30 ms；连续请求在 45 次/分钟后开始被限流（`X-Rl` 归零）。轨迹里"没解析出来"的地址族逐条都能查到（`210.22.*` → AS4837、`221.183.*` → AS9808、`202.97.*` → AS4134、`118.112.*` → AS38283、`154.54.*` → AS174、`2408:8120:*` → AS9929、`2401:8a00:*` → AS10099），所以不是数据覆盖缺口。上游默认 `NextTrace-API` 的 v3 通道在本进程内根本用不了：它需要 NextTrace CLI 建立的 WebSocket 连接（`wshandle.GetWsConn()` 为 nil 时源码直接返回 `TimeOut`），本机实测每个查询 0 ms 失败；而本机带 `TZA_LIVE_TRACE_GEO=IPAPI.com` 跑真实 tracer 时，**每个有地址的跳都解析出了 ASN**。也就是说生产节点用的是 `IPAPI.com` 这类可用源，偶发失败来自该源的限流/超时，不是我们的探测频率。
- 改法：`prefixBackbones` 增加 `2408:8120:` → 9929。IPv6 掩码保留两组十六进制，这个粒度足以把 CUII 的 `/32` 从 联通 `2408::/32` 里分出来；`2408:8000:`/`2408:8001:`/`2408:8762:` 仍是 169，走 `2408:` → 4837 兜底。IPv4 侧的 `210.14.*` 在 /16 粒度无解，靠 Agent 侧真地址兜底（上一节）。
- 验证：`internal/model/model_test.go` 增加"同一 IPv6 轨迹、一个 ASN 都没解析出来"的用例断言 `10099 → 9929`；去掉新条目即失败（退回 `10099 → 4837`，与用户截图一致）。另一处原先把 `2408:8120:*` 断言成 4837 的表项按注册库证据改为 9929。`gofmt -l` 空、`go vet ./...`、`go test ./...` 全绿。
- 上线范围：纯 Server 侧分类器，标签在服务端每次读结果时重算，历史记录与全部节点即刻生效，Agent 不用升级。
